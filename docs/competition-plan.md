# ARMA4OS 下一阶段实施计划

## 当前目标

**先证明真实调度器能可靠运行，再用对照数据决定 Agent 何时切换，最后验证自适应是否有收益。**

项目面向 openEuler，采用 Python 控制面 + Rust 执行器。WSL2 用于开发与联调；最终结论以明确记录的目标环境为准。按两人协作安排，以下阶段以验收结果推进，时间仅作预算。

## 1. 已完成与待完成

| 状态 | 内容 |
| --- | --- |
| 已完成框架 | 采集、画像、目标与策略库、规则路由、Rust 执行器、反馈回滚、Tool / Skill、hook 接口、实验与标定工具 |
| 已验证 | Python / Rust 测试、跨语言模拟闭环、默认调度器压缩烟雾实验；详见[验证记录](validation.md) |
| 下一步 | 真实 scx 加载与恢复、三个场景的静态对比、实测切换成本、真实策略库与在线联调 |
| 最终验收 | 动态收益与消融、openEuler 复现、额外 eBPF hook 实际运行、稳定性与演示 |

当前没有真实 scx / eBPF 加载成功或性能提升的验证结论。用户已确认前期环境问题解决；执行实验时记录当前内核与能力，不再把旧环境问题作为既定阻断条件。

## 2. 接下来五个工作日

本轮唯一交付目标：**获得可信静态对比数据，并在证据支持的上下文中跑通真实 Agent 闭环。** A 负责系统与执行，B 负责负载与实验；分工可按实际情况互换。

| 顺序 / 预算 | A：系统与执行 | B：负载与实验 | 完成标准 |
| --- | --- | --- | --- |
| 第 1 天：真实烟雾测试 | 锁定内核、scx 提交、工具链、二进制与参数；验证一个专家的加载、实际状态和退出恢复；确认比赛允许的 openEuler 版本与内核路径 | 固定 schbench 版本、参数、单位与解析；跑一次默认基线 | 同一负载在默认与一个真实专家下均可运行，有原始输出、sysfs 状态与恢复记录 |
| 第 2 天：冻结正式配置 | 验证默认 + 两个专家，测加载 / 卸载耗时，检查失败恢复和外部占用冲突 | 建立延迟、批处理、混部三场景；短试跑后冻结并发度、预热、测量窗口和缓存规则 | 三个策略可用，三个场景可重放；openEuler 尽早完成一次真实加载验证 |
| 第 3 天：静态矩阵 | 串行切换并核对实际策略，保留异常与恢复证据 | 执行并汇总 3 策略 × 3 场景 × 5 次独立重复 | 45 次正式运行的原始记录、失败列表、区间与对比表；预热另计，噪声大时增加重复 |
| 第 4 天：真实标定 | 复核完整转换成本、真实执行配置与恢复目标 | 从实验生成并复核 Registry 草案，填写机器、上下文、KPI、有效期及成本，配置真实应用 KPI 与有效目标 | 策略库可追溯到独立实验；先用 monitor-only 核对画像、保持 / 切换理由 |
| 第 5 天：在线验证 | 联调真实 apply / rollback、异常与退出清理 | 重放负载序列，比较默认、固定专家与 Agent，记录应用 KPI | 观测 → 决策 → 内核状态 → 反馈可追溯；证据支持时切换，异常能恢复 |

若前一阶段未通过，就先解决阻断问题并顺延后续步骤。框架接口已经实现，本轮主要工作是目标机联调、补齐实际 KPI / 场景和取得证据。

## 3. 首轮只做三个场景

| 场景 | 固定负载 | 必须记录的应用指标 |
| --- | --- | --- |
| 延迟 | schbench；先确认锁定版本实际提供的模式、单位与百分位 | 可用的尾延迟、吞吐或有效工作量，以及测量窗口 |
| 批处理 | 固定输入压缩，或固定源码与并行度的干净编译 | 完成时间、有效吞吐、退出状态 |
| 混部 | schbench + 同一个批处理任务，后台覆盖主要测量窗口 | 前台尾延迟 + 后台进度 / 完成时间；预先声明前台 SLO 与后台约束 |

候选从 **内核默认 + scx_bpfland + scx_rusty** 开始，按目标内核兼容性替换不可用专家，不预设哪个更优。现有默认配置只有压缩烟雾任务，需补齐延迟和混部场景，不能直接当作完整矩阵。

实验必须遵守：

- 同一内核、同等资源下串行运行，按轮次随机化策略顺序；记录版本、参数、资源分配、随机种子和实际顺序。
- 探索数据与正式评估分开；正式配置冻结后至少 5 次独立重复，一次运行中的采样窗口不算独立重复。
- 每次使用新结果目录，保存 manifest、逐 trial 记录、原始 stdout/stderr 和实际调度状态；Agent 运行另保存指标、决策、动作与反馈。
- summary 从原始记录重建；超时、非零退出、解析失败和记录缺失显式报告。模拟成绩不进入真实策略库，无收益结果同样保留。
- 在线路由使用实际观测与应用目标，不能输入 benchmark 的未来阶段标签。全程成绩包含监控和切换开销，不删掉不利过渡段。

## 4. 静态实验之后怎么决定

| 实验结果 | 下一步 |
| --- | --- |
| 不同上下文适合不同专家，差异超过噪声 | 进入动态选择实验，验证 Agent 能否识别上下文并覆盖切换成本 |
| 一个固定策略始终更好 | 将其作为固定对照，检查目标或负载变化是否产生真实选择需求，再决定是否扩大场景 |
| 专家均无可信收益 | 检查 CPU 争用、瓶颈、参数和测量方法；先保留负结果，暂缓模型训练 |
| 加载或恢复不可靠 | 暂停正式矩阵，修复执行路径后重新验证；不使用受污染数据标定 |

## 5. 后续验收顺序

1. **动态与消融实验**：在未参与标定的负载序列上，比较默认、各静态专家、只监控 Agent、完整 Agent，以及从独立标定数据选出的最佳固定策略。报告全程 KPI、SLO 违约时间、后台进度、切换次数与开销。
2. **验证项目机制**：同一负载改变目标，检查决策是否合理变化；改变阶段长度，对比计入 / 不计切换成本；对比启用 / 关闭反馈回退。规则有效后，再决定是否训练树模型。
3. **openEuler 主实验与扩展**：在已确认可加载的目标环境重跑主结果，单独验证额外 eBPF hook 与授权 cgroup 控制的生命周期和恢复。扩展动作与 CPU 主实验分开，避免混淆收益来源。
4. **稳定性与交付**：至少两小时固定脚本运行与故障恢复演练；由另一人从干净环境复现。提交版本锁定、配置、原始数据、汇总脚本、性能报告与演示流程。

核心主张是“应用目标、证据和切换成本共同约束选择，持续反馈负责恢复”。是否成立由上述实验判断，架构组合本身不等于创新或性能收益。

## 6. 本轮范围与资料入口

优先把预算用于真实 CPU 调度、可靠恢复、应用 KPI 和复现实验。小模型、低频 LLM、MCP 网络接入、layered 调参在主线数据支持后再做；若正式赛题明确要求 LLM，再提升其优先级。自生成调度器、在线 RL、完整多 Agent 系统和复杂看板暂不进入本轮。

- 运行、配置与标定步骤：[运行与扩展指南](framework-guide.md)。
- 模块职责、ASA / SchedCP 方法映射及成本模型：[架构](architecture.md)；动作字段与恢复语义：[执行协议](protocol.md)。
- 原始论文：[ASA](https://arxiv.org/html/2511.11628v1)、[SchedCP](https://arxiv.org/html/2509.01245v4)。借鉴专家路由、时间稳定与工具化控制面，当前实现不宣称端到端复现论文。
- 目标机兼容性依据：[scx](https://github.com/sched-ext/scx)、[Linux sched_ext](https://docs.kernel.org/scheduler/sched-ext.html)。实际实验锁定提交与内核组合；WSL 结果不直接等同于原生 openEuler 结果。
